# CoLUI Systematic Debugging

Сначала установи корневую причину, затем предлагай и реализуй исправление.
Не меняй рабочий код на основании догадки. Соблюдай корневой `AGENTS.md`.

Навык переносит только systematic debugging из obra/superpowers и адаптирует
его к CoLUI. Не подключай другие процессы Superpowers. После подтверждения
причины используй проектный `.agents/skills/tdd/SKILL.md`, если он доступен.
Если его нет, выполни встроенный в раздел 5 цикл RED → GREEN → REFACTOR.

## 1. Зафиксировать симптом

- Запиши точное наблюдаемое поведение, ожидаемое поведение и минимальные условия.
- Прочитай полное сообщение об ошибке, цепочку причин, stack trace, stderr,
  код возврата и имена упавших тестов. Не делай вывод из последней строки.
- Получи минимальную воспроизводимую команду. Убедись, что фильтр действительно
  выбрал нужный тест: ноль тестов, `skipped` и ошибка окружения не воспроизводят баг.
- Повтори воспроизведение только когда это помогает отличить стабильный дефект
  от гонки. Для зависания используй ограниченный внешний timeout и сохрани место,
  где выполнение перестало продвигаться.
- Проверь `git status`, текущий diff и недавние релевантные изменения. Не смешивай
  исходную проблему с эффектом незакоммиченных пользовательских изменений.

Не исправляй ничего на этом этапе. Допустимы временные наблюдения и диагностические
сообщения, если они минимальны, не раскрывают секреты и затем удаляются либо
осознанно остаются полезной диагностикой.

## 2. Локализовать границу отказа

CoLUI проходит через несколько границ:

`React → src/ipc → Tauri command/DTO → colui-app port → adapter → Docker/filesystem`.

Проверяй вход и выход на каждой релевантной границе, начиная с самой узкой:

- UI: действие пользователя, query key, mutation, инвалидированное состояние.
- IPC: имя команды, payload, Rust DTO, сериализованный ответ, Zod decode.
- App: выбранный use case, профиль/revision, lock, runtime session и generation.
- Adapter: argv и cwd Compose, очищенное окружение, Docker endpoint/fingerprint,
  registry bytes/identity и inventory observation.
- External: доступность Docker socket/CLI, версия Compose, права файловой системы.

Не печатай всё окружение, содержимое env-файлов, credentials или необработанные
данные профиля. Для fingerprint, ID и путей выводи только минимум, необходимый
для различения границ.

Если плохое значение обнаружено глубоко, проследи его назад:

1. Где значение впервые стало неверным?
2. Кто передал его в эту функцию или слой?
3. Где оно было создано, декодировано, закэшировано либо признано актуальным?
4. Какой инвариант должен был остановить его раньше?

Исправление должно воздействовать на источник или отсутствующий инвариант,
а не скрывать последнюю ошибку в цепочке.

## 3. Сравнить с рабочим путём

- Найди ближайший рабочий пример в том же слое и прочитай его вместе с тестами.
- Сравни входы, состояние, session/revision/generation, locks, query keys,
  feature flags, environment и порядок async-событий.
- Перечисли фактические различия. Не отбрасывай различие без проверки.
- Проверь предположения о сторонней библиотеке по её фактической версии в lockfile
  и локальной документации/исходникам; при необходимости используй первичный источник.

Особенно проверь типичные границы CoLUI:

- `cargo test --workspace` не запускает runtime-target, которому нужна feature
  `test-support`.
- Browser smoke с mock IPC не подтверждает работу Tauri или реального Docker.
- `unavailable`, `stale` и пустой результат имеют разный смысл.
- Событие инвалидирует кэш, но polling может восстанавливать пропущенное событие.
- Docker API и Compose CLI должны относиться к одной runtime session/fingerprint.
- Inventory refresh не должен запускать Compose config или писать реестр.

## 4. Проверить одну гипотезу

Сформулируй одну проверяемую гипотезу:

> Причина — X, потому что наблюдение Y возникает на границе Z; если это верно,
> минимальная проверка W даст результат Q.

Проверь одну переменную минимальным способом. Предпочитай наблюдение, узкий тест
или временную instrumentation вместо изменения поведения. Если результат
противоречит прогнозу, отвергни гипотезу и вернись к собранным данным.
Не наслаивай несколько предполагаемых исправлений.

Для гонок и async-кода ожидай проверяемое состояние или событие. Произвольный
`sleep` допустим только как внешний предохранитель теста, а не доказательство
порядка событий.

Считай корневую причину подтверждённой, когда доказаны:

- конкретный источник неверного состояния или решения;
- путь от источника до симптома;
- минимальная проверка, отличающая эту причину от альтернатив.

Если воспроизведение невозможно, сообщи подтверждённые факты, исключённые версии
и недостающие данные. Не представляй наиболее вероятную версию как факт.

## 5. Исправить через TDD

После подтверждения причины прочитай `.agents/skills/tdd/SKILL.md`, если
он существует. В любом случае выполни следующий цикл:

1. Добавь минимальный regression-тест, воспроизводящий симптом через публичную
   границу правильного слоя.
2. Запусти его на неизменённой реализации и подтверди ожидаемый RED.
3. Внеси одно минимальное исправление корневой причины.
4. Получи GREEN на том же тесте, затем запусти связанные и обязательные проверки.
5. Только после GREEN выполни необходимый рефакторинг.

Не ослабляй assertions, не заменяй дефект mock-поведением и не добавляй обходной
fallback, который превращает typed error в пустой результат.

Если исправление не сработало, откати только собственную неподтверждённую попытку
без потери пользовательских изменений и вернись к исследованию. После трёх
независимых неудачных гипотез остановись: собери доказательства возможной
архитектурной проблемы и обсуди изменение конструкции перед четвёртой попыткой.

## Узкие команды для диагностики

Проверяй актуальные scripts и manifests перед запуском.

| Область | Пример узкой команды |
| --- | --- |
| Frontend/IPC | `pnpm exec vitest run <test-file> -t '<test-name>'` |
| Domain | `cargo test -p colui-domain <test-name>` |
| App use case | `cargo test -p colui-app --test <target> <test-name>` |
| Adapter | `cargo test -p colui-adapters --test <target> <test-name>` |
| Runtime/Compose | `cargo test -p colui-adapters --features test-support --test runtime <test-name>` |
| DTO contract | `cargo test -p colui-tauri --test dto_contracts <test-name>` |
| Architecture boundary | `bash scripts/check-boundaries.sh` |

Для проблем, проявляющихся только с Docker, сначала отдели ошибки окружения от
логики герметичными fake-тестами. Реальный интеграционный запуск выполняй через
`cargo test -p colui-adapters --features docker-tests --test docker` только с
временными ресурсами fixture.

## Отчёт о результате

Перед завершением укажи:

- воспроизведение: команда и наблюдаемый симптом;
- корневая причина: подтверждающее доказательство и путь до симптома;
- RED/GREEN: regression-тест и результат до/после исправления;
- проверка: связанные suites и непротестированные области;
- временная instrumentation: удалена или оставлена с обоснованием.

Для запроса только на диагностику остановись после подтверждения причины и отчёта.
Не реализуй исправление, если пользователь его не просил.
