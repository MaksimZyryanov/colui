# CoLUI TDD

Следуй циклу RED → GREEN → REFACTOR. Первое изменение поведения рабочего кода
допустимо только после запуска теста, упавшего из-за отсутствующего поведения
или воспроизводимого бага. Чтение кода и диагностика перед тестом допустимы.

Навык самодостаточен: он переносит только TDD из obra/superpowers.
Не подключай остальные навыки Superpowers, не вводи обязательные brainstorming,
планы-файлы, subagents, worktrees, коммиты или PR. Соблюдай применимые AGENTS.md
и поручение пользователя; этот навык не даёт дополнительных разрешений.

## Подготовка

1. Убедись, что работаешь с CoLUI. Прочитай применимые AGENTS.md, затронутый код
   и соседние тесты. Проверь текущие package.json/Cargo.toml: команды ниже —
   ориентир, не повод менять проект под устаревшую инструкцию.
2. Выбери одно проверяемое поведение и слой, которому оно принадлежит.
   Сформулируй, какой реальный дефект должен поймать тест. Ожидание выведи из
   требования, а не из текущей реализации или её helper-функции.
3. Выбери самый узкий тестовый target. Если есть сомнения в исправности среды,
   сначала запусти соседний существующий тест. Не запускай все suites в каждом цикле.

## RED: тест до реализации

- Напиши минимальный тест одного поведения. Для багфикса воспроизведи дефект
  через публичный интерфейс соответствующего слоя.
- Запусти тест на неизменённой реализации и проверь, что он действительно выбран
  фильтром и выполнен. Ноль тестов, skipped и таймаут запуска не являются RED.
- Убедись, что причина падения соответствует требованию. Опечатка, неверный import,
  отсутствие Cargo/Docker/браузера или сломанный fixture не доказывают баг.
- Если тест сразу проходит, выясни, реализовано ли поведение или сценарий не ловит
  дефект. Не ломай рабочий код специально ради красного результата.
- Для нового Rust API ошибка компиляции сама по себе не доказывает поведение.
  После написания теста допустим только минимальный каркас API без реализации
  поведения, чтобы получить исполняемый тест с ожидаемым падением. Не включай в
  каркас рабочую логику; явно отличай каркас от GREEN-реализации.
- Кратко зафиксируй точную команду, тест и фактическую причину падения в ходе работы.

Если среда блокирует запуск, попробуй доступный герметичный тест того же контракта.
Если ожидаемый RED всё равно нельзя наблюдать, подготовь тест и опиши блокер;
не переходи молча к реализации и не заявляй о выполненном TDD. Продолжение без
проверенного RED допустимо только по явной инструкции пользователя.

## GREEN: минимальная реализация

- Измени только необходимый рабочий код. Сохраняй архитектурные границы CoLUI.
- Запусти тот же тест, затем связанные тесты затронутого модуля.
- Исправляй реализацию, если она не удовлетворяет корректному тесту.
  Если ошибочно само ожидание, обоснуй исправление теста и заново докажи RED
  на безопасно изолированной версии без текущего исправления.
- Не подменяй проверяемую логику mock-ответом, не удаляй assertions и не меняй
  ожидания только ради зелёного прогона.

## REFACTOR и следующий цикл

Рефакторь после GREEN, сохраняя поведение и повторяя связанные тесты.
Новое поведение начинай с нового RED. Не добавляй отдельный тест на каждую
тривиальную функцию ради количества или покрытия.

Для задачи только на рефакторинг сначала используй существующие поведенческие
тесты и при пробелах добавь characterization-тесты: они могут сразу проходить.
Не создавай искусственный дефект ради RED. Изменение поведения внутри такой
задачи требует отдельного обычного TDD-цикла.

Если ты уже написал реализацию до теста, остановись. Сохрани пользовательские
изменения. Изолируй только собственное исправление, докажи падение теста на версии
без него и затем минимально реализуй поведение. Не удаляй чужой код и не используй
широкие reset/checkout для имитации правильной последовательности. Честно отметь
нарушение первоначального порядка.

## Выбор слоя и команд CoLUI

Команды выполняй из корня. Замени плейсхолдеры реальными путями/именами;
проверь, что фильтр выбрал нужный тест.

| Поведение | Где тестировать | Узкий запуск |
| --- | --- | --- |
| Доменные инварианты | crates/colui-domain/tests или unit-модуль | `cargo test -p colui-domain <test_name>` |
| Use cases, revisions, блокировки, сессии | crates/colui-app/tests, doubles портов | `cargo test -p colui-app --test <target> <test_name>` |
| Registry, inventory, адаптеры | crates/colui-adapters/tests | `cargo test -p colui-adapters --test <target> <test_name>` |
| Compose/runtime-процессы | runtime target и существующий fake executable | `cargo test -p colui-adapters --features test-support --test runtime <test_name>` |
| Rust DTO | src-tauri/tests/dto_contracts.rs | `cargo test -p colui-tauri --test dto_contracts <test_name>` |
| TS IPC и Zod | src/ipc/__tests__ | `pnpm exec vitest run <test_file> -t '<test_name>'` |
| React-сценарий | src/features/*/__tests__, Testing Library | `pnpm exec vitest run <test_file> -t '<test_name>'` |

- Domain: проверяй инвариант без инфраструктуры. App: используй существующие порты;
  не вноси Docker API/CLI во внутренние слои ради теста.
- Adapters: используй временные файлы, fake executable и контролируемые зависимости.
  Для процессов проверяй наблюдаемое завершение и вывод; не полагайся на случайные sleep.
- UI: проверяй действия и результат пользователя, используя настоящие компоненты.
  Пример — сохранить черновик, закрыть и открыть форму, увидеть восстановленные поля;
  один `localStorage.setItem` этого не доказывает.
- Mock только внешнюю границу, а не проверяемую логику. Spy на аргументы, порядок
  или число вызовов допустим, когда это и есть контракт порта. Fixture должен
  соответствовать реальному DTO, включая обязательные поля.
- IPC: начни с теста ожидаемого контракта; согласуй Rust DTO, Zod, mock backend
  и fixtures. Генерируемые файлы обновляй через `bash scripts/generate-schemas.sh`,
  не вручную. После изменений проверяй обе стороны границы.
- Не используй пользовательские Docker-проекты для тестов. Реальный Docker —
  отдельная интеграционная проверка с временными ресурсами, не условие каждого RED.

## Финальные проверки и доказательства

Выполни применимые проверки AGENTS.md. Если его нет, используй:

- TS/React: `pnpm typecheck`, `pnpm test`; UI/сборка: также `pnpm build`.
- Rust: `cargo test --workspace`; runtime: также feature-gated runtime-target выше.
- IPC: `pnpm test:contracts` и `cargo test -p colui-tauri --test dto_contracts`.
- Границы слоёв/зависимости: `bash scripts/check-boundaries.sh`.

Не повторяй уже покрытые suites без причины. Workspace-прогон Rust без
`test-support` не включает отдельный runtime-target адаптеров. Browser mock
не доказывает работу Tauri/Docker. Если нужно проверить реальную интеграцию,
используй `cargo test -p colui-adapters --features docker-tests --test docker`
в подготовленной среде и явно сообщай о пропусках.

В итоговом отчёте кратко укажи:

- RED: тест, команда, наблюдавшаяся причина падения до исправления.
- GREEN: что изменено и результат повторного запуска.
- Регрессии: какие связанные проверки прошли; что не запускалось или заблокировано.

Не называй test-first работу, для которой видел только зелёный прогон после
реализации. Не выдавай отсутствие окружения или исходное падение за успешный тест.
Для документации, чистой косметики и генерируемого вывода не изобретай тесты на
текст исходников; изменение поведения генератора/скрипта проверяй исполнением.
