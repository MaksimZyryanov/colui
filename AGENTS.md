# AGENTS.md

Инструкции для AI-агентов, работающих с CoLUI. Файл предназначен для корня
репозитория. Вложенный `AGENTS.md` дополняет эти правила и имеет приоритет
при конфликте в своей области. Явные инструкции пользователя имеют приоритет.

## Проект и источники информации

CoLUI — macOS-приложение для управления локальными Docker Compose-проектами
и отдельными контейнерами. Стек: React, TypeScript, TanStack Query, Tauri, Rust.

- `docs/README.md` — навигация по документации.
- `docs/architecture.md` — текущая архитектура и владение данными.
- `docs/history/` и `docs/design/` — история и обоснования решений; записи
  могут описывать состояние на момент написания.
- Код и тесты показывают текущее поведение, но не делают обнаруженный баг нормой.
  При расхождении с требованиями выясни причину, не закрепляй ошибку автоматически.

Перед изменением прочитай затронутый модуль и ближайшие тесты. Сохраняй
пользовательские изменения; избегай несвязанных рефакторингов и форматирования.

## Архитектура и границы

Проект — модульный монолит. Направление зависимостей Rust-кода:
`colui-tauri → colui-adapters → colui-app → colui-domain`.
Допускаются прямые зависимости на более внутренние слои.
Это направление импортов, а не порядок вызовов: use cases вызывают адаптеры
через порты, определённые во внутреннем слое.

| Путь | Ответственность и ограничения |
| --- | --- |
| `crates/colui-domain` | Доменные модели, валидация, инварианты. Не зависит от других крейтов приложения, Tauri, Docker, файловой системы или процессов. Допускаются библиотеки доменных типов и сериализации, например `uuid` и `serde`. |
| `crates/colui-app` | Use cases и порты (traits). Зависит от domain; внешние операции выполняет через порты, без прямых Docker CLI/API-вызовов. |
| `crates/colui-adapters` | Реализации портов: Docker API, Compose, реестр, inventory, recovery. Зависит от app/domain, не от Tauri. |
| `src-tauri` | Сборка зависимостей, Tauri-команды, DTO и desktop shell. Бизнес-правила остаются в app/domain. |
| `src/ipc` | Единственная frontend-граница вызовов и событий backend; обёртки команд, Zod-декодирование и нормализация ошибок. |
| `schemas/` | JSON Schema и контрактные fixtures. Генерируемые файлы обновляются через Rust-генератор; Zod-схемы проверяются на согласованность с ними. |
| `src/features` | React-фичи, хуки и отображение состояния. Backend доступен только через `src/ipc`; разрешены общие UI-компоненты и существующие frontend-библиотеки. |

Не обходи `scripts/check-boundaries.sh` и не ослабляй проверки ради прохождения.

## Инварианты, которые нужно сохранять

- Lifecycle-команды принимают ID профиля; backend под защитой операции перечитывает
  профиль и определяет пути, аргументы Compose и окружение. Не принимай произвольные
  CLI-аргументы или командные строки из UI и не заменяй argv-вызовы shell-строками.
- `RuntimeGateway` владеет соединением и идентичностью Docker API/CLI.
  Не обходи проверки fingerprint и блокировку Compose при `contextMismatch`.
- Сохраняй проверки runtime session, revision и generation. Устаревшие ответы
  не должны заменять более новое состояние или разрешать действия в другой сессии.
- `InventoryCoordinator` владеет runtime-контейнерами и их связями. Fast inventory
  refresh читает Docker API, не запускает `docker compose config` и не пишет реестр.
  Автоматическая регистрация — отдельный use case с проверками и блокировками.
- Сохраняй существующий протокол `OperationLockManager` для мутаций профилей,
  lifecycle и recovery; не создавай параллельный механизм владения операциями.
- Реестр сохраняет optimistic revision-проверки, атомарную запись, синхронизацию
  на диск, резервные копии и восстановление. Не подменяй повреждённые данные
  пустым реестром и не перезаписывай их молча.
- Изменения управления процессами должны учитывать общий deadline, завершение
  группы потомков, reap и ограниченное ожидание stdout/stderr. Вывод ограничен
  по размеру; диагностические сообщения не раскрывают секреты или всё окружение.
- Ошибка IPC, недоступный runtime и отсутствие наблюдений не равны пустому списку
  проектов. Сохраняй типизированные ошибки и различие unavailable/stale/empty.
- Используй существующие query keys, события инвалидации и владельцев polling.
  Не добавляй независимые циклы опроса в каждый компонент.

## Правила изменений

### Контракты IPC

1. Обнови Rust DTO, их маппинг и при необходимости доменные типы.
2. Обнови генератор схем/fixtures в `src-tauri/src/schema_generation.rs`.
3. Выполни `bash scripts/generate-schemas.sh`; просмотри diff схем и fixtures.
   Не правь генерируемые результаты вручную. Для дополнительных ручных fixtures
   сначала проверь, что они не принадлежат генератору.
4. Согласуй Zod-схемы, типы, обёртки, события и затронутый `src/ipc/mock-backend.ts`.
5. Проверь Rust DTO и TS-контракты. Изменение протокола должно проверяться на обеих
   сторонах границы, включая отрицательные случаи, когда это применимо.

### UI и тесты

- Используй существующие UI-компоненты и Radix-примитивы для диалогов и меню.
  Сохраняй доступные названия элементов, клавиатурное управление и фокус.
- Новый доменный инвариант и исправление поведенческого бага сопровождай
  содержательным тестом в соответствующем слое.
- Проверяй наблюдаемый результат и полный сценарий: например, сохранение
  черновика и его восстановление, а не только вызов `localStorage.setItem`.
- Для процессов проверяй ошибки, таймаут и случай, когда родитель завершился,
  а потомок продолжает удерживать каналы вывода.
- Не меняй ожидаемые результаты тестов только ради зелёного прогона.
  Для чисто текстовых и косметических правок не добавляй формальные тесты.

### Зависимости и документация

- Сначала используй существующие зависимости. Новую зависимость обоснуй в отчёте;
  существенное расширение стека или архитектуры согласуй с пользователем.
- Сохраняй lockfiles. Для установки зафиксированных зависимостей используй
  `pnpm install --frozen-lockfile`; при намеренном изменении зависимостей обнови
  lockfile обычным `pnpm install` и проверь diff. Используй pnpm из `packageManager`.
- Не переписывай `docs/history/*`, если задача явно этого не требует.
  Обновляй README и текущие инструкции при изменении поведения или команд.
  Новое архитектурное решение документируй, не переписывая молча старые записи.

## Проверки

Все команды выполняются из корня репозитория. Выбирай проверки по затронутому
поведению; для изменений нескольких областей объединяй наборы без повторов.
На время разработки допустимы точечные тесты, перед завершением — применимые
проверки из таблицы. Для проверки только документации Rust/UI-прогон не нужен.

| Область изменения | Проверки |
| --- | --- |
| Только документация | Проверить ссылки, пути и команды; `git diff --check` |
| TypeScript / React | `pnpm typecheck`, `pnpm test` |
| UI, frontend-сборка или её зависимости | Дополнительно `pnpm build`; для пользовательских сценариев — визуальная проверка и применимый `pnpm test:browser` |
| Rust | `cargo fmt --all -- --check`, `cargo test --workspace` |
| Runtime, Compose, процессы или связанные порты | Дополнительно `cargo test -p colui-adapters --features test-support --test runtime` |
| IPC-контракт | Генерация схем; `cargo test -p colui-tauri --test dto_contracts`, `pnpm test:contracts`, `pnpm typecheck` |
| Импорты, зависимости или границы ответственности | `bash scripts/check-boundaries.sh` |
| Boundary-checker | Дополнительно `bash scripts/check-boundaries.sh --self-test` |

`cargo test --workspace` без feature `test-support` не запускает отдельный
runtime-target адаптеров. `pnpm test` уже включает `pnpm test:contracts`, а
workspace-прогон Rust включает DTO-тесты: не повторяй их без причины.

Для изменений Docker-интеграции в среде с доступным daemon:

```bash
cargo test -p colui-adapters --features docker-tests --test docker
```

Используй только временные ресурсы тестовой fixture; не изменяй существующие
пользовательские проекты для проверки. Пропуск из-за отсутствия Docker не
считается успешной проверкой интеграции.

Для ручной desktop-проверки на macOS с Rust и Docker:

```bash
pnpm build
cargo run -p colui-tauri --bin colui-tauri
```

Browser smoke использует mock IPC и требует установленного браузера Playwright;
он не заменяет проверку Tauri и реального Docker. Не запускай GUI как обычный
завершающийся тест и не оставляй запущенные тобой проверочные процессы.

### Если проверка не проходит

Исправляй регрессии, вызванные текущими изменениями. Если причина — исходное
падение или ограничение среды, зафиксируй команду, причину и непроверенную область.
Если происхождение падения не установлено, так и напиши. Не заявляй, что проверка
успешна, не отключай её и не расширяй задачу на посторонние исправления без нужды.
Не повторяй зависший прогон без новой гипотезы; останови его и отрази ограничение.

## Коммиты, PR и итоговый отчёт

- Один коммит — один связный, проверяемый набор изменений. Не разделяй атомарное
  изменение DTO, схем и UI только ради отдельных коммитов по слоям.
- Следуй принятому стилю сообщений; объясняй, что изменилось и зачем.
- В PR и итоговом отчёте укажи поведение после изменения, выполненные проверки,
  пропуски/падения и оставшиеся ограничения. Отличай проверенное от предположений.
- Не создавай коммит, не отправляй изменения и не публикуй релиз, если это
  не входит в поручение пользователя.
