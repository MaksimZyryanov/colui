# Задача: объединить UI раздела Projects в единый список ресурсов (в стиле OrbStack)

## Контекст

Репозиторий: `MaksimZyryanov/colui` — macOS-приложение (Tauri + React + Rust) для управления
локальными Docker Compose проектами и отдельными контейнерами.

Сейчас раздел **Projects** (`src/features/projects/ProjectsView.tsx`) состоит из трёх
визуально и структурно независимых секций:

1. **Registered projects** — карточки `ProfileCard` (`src/features/projects/components/ProfileCard.tsx`)
   с меню действий `ActionMenu` (`src/features/projects/components/ActionMenu.tsx`).
2. **Discovered projects** — секция `DiscoverySection` (`src/features/discovery/DiscoverySection.tsx`)
   с карточками кандидатов `CandidateCard` (`src/features/discovery/CandidateCard.tsx`).
3. **Other containers** — секция `OtherContainers` (`src/features/containers/OtherContainers.tsx`)
   с карточками `ContainerCard` (`src/features/containers/ContainerCard.tsx`).

Каждая секция реализует свой визуальный язык и свой набор действий для, по сути, одного и
того же типа сущности («ресурс, за которым нужно следить» — compose-проект или контейнер).
Это увеличивает когнитивную нагрузку: пользователю приходится помнить, в какой из трёх зон
искать нужный элемент, и учиться трём разным паттернам взаимодействия.

## Цель

Заменить три раздельные секции на **единый список ресурсов**, вдохновлённый паттерном
OrbStack (сворачиваемые группы + плоские строки standalone-контейнеров в одном списке,
действия скрыты до hover, поиск сверху), сохранив всю текущую бизнес-логику и IPC-контракты
без изменений — задача чисто фронтенд-UI/UX, без изменений в Rust-бэкенде.

## Целевой дизайн

### Структура

Один список внутри `ProjectsView`, обёрнутый в единый контейнер с рамкой (не три отдельных
блока). Строки трёх типов:

1. **Зарегистрированная compose-группа** (данные из текущего `ProfileCard`/профилей):
   - строка-заголовок группы: chevron (expand/collapse), статус-точка (running/stopped/error —
     по текущей логике статуса профиля), имя проекта, бейдж `registered`, действия по hover
     (Restart, Stop, `⋯`-меню с Apply/Tear down/Remove — переносится из текущего `ActionMenu`
     без изменения списка пунктов и подтверждающих диалогов);
   - при развороте — дочерние строки с контейнерами этого проекта (индент, приглушённый
     стиль, минимальный набор действий — например, просмотр логов).

2. **Обнаруженная, но не зарегистрированная compose-группа** (данные из текущего
   `CandidateCard`/`useDiscovery`):
   - визуально та же строка-группа, но приглушённая (серый/пунктирный акцент), бейдж
     `discovered` вместо `registered`;
   - вместо hover-действий — всегда видимая инлайн-кнопка **Register** (текущий вызов
     `registerCandidate`) и вторичное действие **Ignore** (в `⋯`-меню или по hover);
   - при `NameConflict`/`IncompleteMetadata` — тот же ряд, но с иконкой предупреждения и
     тултипом/подписью, поясняющей причину (конфликт имени / неполные метаданные), без кнопки
     Register (сохранить текущую бизнес-логику классификации кандидатов как есть).

3. **Standalone-контейнер** (данные из текущего `ContainerCard`/`OtherContainers`):
   - плоская строка без chevron: статус-точка, имя, бейдж `standalone`, действия по hover
     (Start/Stop/Restart, View logs, порт-биндинги — сохранить текущую логику Copy/Open из
     `PortBindings.tsx`).

Все три типа строк отсортированы вместе в одном списке (например, по имени), а не разнесены
по отдельным блокам.

### Общие элементы

- **Строка поиска/фильтра** над списком: фильтрует по имени проекта/контейнера в реальном
  времени на клиенте (client-side filter, без нового IPC). При необходимости — фильтр-чипы по
  статусу (Running / Stopped / Discovered), но это опционально и может быть отдельной итерацией.
- **Действия по hover**: в состоянии покоя строка показывает только статус-точку, имя и бейдж;
  иконки действий появляются при наведении/фокусе на строку (для доступности — также по
  клавиатурному фокусу, не только по мыши).
- **Диалоги подтверждения** (`Tear down`, `Remove profile`, `Restore backup` — если применимо)
  остаются без изменений по поведению, меняется только точка входа (то же `⋯`-меню, но внутри
  новой строки).
- **`Add Project`** остаётся отдельной кнопкой в шапке раздела (открывает существующий
  `ProfileFormDialog`), не встраивается в список.
- **`Automatic: On/Off`** и **`Register eligible now`** для авторегистрации остаются в шапке
  раздела (или в компактной панели над списком), как элементы управления, не привязанные к
  конкретной строке.

### Что явно НЕ меняется

- Раздел **Diagnostics** и вся его логика — вне скоупа этой задачи.
- Никакие Rust/IPC-контракты, DTO, хуки данных (`useDiscovery`, `useDiscoveryMutations`,
  `useProfiles`/аналог для профилей, хуки для standalone-контейнеров) — не меняются.
  Переиспользуются как есть.
- Классификация кандидатов (`NewUnambiguous` / `NameConflict` / `IncompleteMetadata` /
  `AlreadyRegistered`), auto-registration dedup/retry — бизнес-логика на бэкенде не трогается.
- Все существующие диалоги подтверждения (текст, кнопки, focus-management) переносятся как
  есть, без изменения формулировок.

## Предлагаемая структура компонентов

Создать общий слой компонентов списка вместо трёх параллельных наборов карточек:

```
src/features/projects/components/
  ResourceList.tsx        — контейнер списка + поиск/фильтр, сортировка/группировка строк
  ResourceGroupRow.tsx     — строка-группа (registered / discovered compose-проект),
                             с вариантом visual state: "registered" | "discovered"
  ResourceChildRow.tsx     — дочерняя строка контейнера внутри развёрнутой группы
  ResourceItemRow.tsx      — плоская строка standalone-контейнера
  RowActions.tsx           — общий набор hover-actions (иконки + `⋯`-меню), параметризуемый
                             списком доступных действий на конкретную строку
```

`ProfileCard`, `CandidateCard`, `ContainerCard`, `ActionMenu` в текущем виде — либо
удаляются и заменяются вызовами новых компонентов, либо (если содержат специфичную логику
диалогов) рефакторятся так, чтобы рендерить только содержимое диалогов, а разметку строки
отдают новым `Resource*Row` компонентам. Решение — на усмотрение исполнителя, главный критерий:
не дублировать три похожих визуальных паттерна.

`ProjectsView.tsx` перестаёт рендерить три отдельные секции (`ProfileCard`-список,
`DiscoverySection`, `OtherContainers`) и вместо этого собирает единый массив ресурсов из трёх
существующих источников данных (профили, discovery-кандидаты, standalone-контейнеры),
передавая его в `ResourceList`.

## Критерии приёмки

1. В разделе Projects визуально один список с одной рамкой, без трёх отдельных заголовков
   секций «Registered projects» / «Discovered projects» / «Other containers».
2. Зарегистрированный compose-проект разворачивается/сворачивается и показывает свои
   контейнеры.
3. Обнаруженный, но не зарегистрированный проект отображается в том же списке визуально
   приглушённым, с кнопкой Register прямо в строке.
4. Standalone-контейнер отображается плоской строкой в том же списке.
5. Действия (Stop/Restart/Apply/Tear down/Remove/Register/Ignore/View logs/Start) доступны
   и функционально идентичны текущему поведению — просто через новую разметку строк с
   hover/focus-раскрытием.
6. Поиск по имени фильтрует все три типа строк одновременно.
7. Все существующие диалоги подтверждения (Tear down, Remove profile и т.д.) работают без
   изменений в поведении и тексте.
8. Клавиатурная доступность сохранена: каждая строка и её действия достижимы по Tab/Enter,
   меню возвращает фокус на триггер при закрытии (как указано в текущей архитектуре).
9. Diagnostics и всё, что вне Projects, не затронуто.
10. Существующие тесты (Vitest/frontend) для затронутых компонентов обновлены/переписаны под
    новую структуру; `pnpm typecheck`, `pnpm test`, `pnpm build` проходят.

## Вне скоупа (не делать в рамках этой задачи)

- Изменение бизнес-логики авторегистрации (persist настройки между сессиями — отдельная
  задача, обсуждалась ранее, но НЕ входит в этот таск).
  - Изменение раздела Diagnostics.
- Замена модального диалога логов (`ContainerLogsDialog`) на боковую панель — возможное
  улучшение будущего, не часть этой задачи.
- Изменения в Rust-крейтах (`crates/colui-domain`, `crates/colui-adapters`, `crates/colui-app`,
  `crates/colui-tauri`).

## Референс

Целевой визуальный паттерн — приложение OrbStack: единый список Docker-ресурсов, где
compose-проекты — сворачиваемые группы, а отдельные контейнеры — плоские строки в том же
списке; действия появляются при наведении, статус кодируется цветной точкой.
